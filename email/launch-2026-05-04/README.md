## Audience copy choice

We had two written variants:

- **Variant A** — "We kept our promise" (waitlist-flavored, gratitude lead-in)
- **Variant B** — "Web is now live" (existing-users-flavored, transactional)

We're sending **Variant A to all 37 recipients**. Rationale: the gratitude framing actually lands harder for the 14 people who joined the waitlist *and then* signed up — they were the most-believing early users. The 9 waitlist-only recipients see exactly the message they signed up to receive. The remaining 14 user-only recipients get a slightly more emotional message than they strictly need, but it doesn't read off-key.

## Why hand-coded HTML over Canva

This was a real fork in the road. Canva exports email designs as a single image wrapped in HTML. We did not go that way. Reasons, in priority order:

1. **Image-only emails are a deliverability red flag.** Gmail and Outlook spam filters down-rank them, and roughly 30% of corporate Outlook installs block images by default. Those recipients see nothing.
2. **No real links.** The whole email becomes one clickable image with one wrapping `<a>`. We lose the per-link tracking, the `mailto:`/`tel:` hooks, and accessible alt text.
3. **Dark-mode breaks weirdly.** Image-as-email gets background-inverted on Apple Mail and Outlook dark themes. Logos go from white-on-blue to ghost-on-blue. With real HTML we can lock the color scheme.
4. **No personalization.** "Hola {{firstName}}" needs server-side templating, which only works against text/HTML, not a baked-in image.
5. **No mobile fluidity.** Images downscale badly. Real HTML uses media queries.

The path we took: design in our heads / iterating-in-browser, build with email-safe HTML (tables, inline CSS, `mso` conditionals for Outlook), send via the Trigger Email Firebase extension already wired to the project.

## Brand fidelity

Everything matches `Oqupa-website/src/index.css` lines 5–26.

### Typography
- **Roboto Serif** — primary heading face. Used on the H1 (`Oqupa ya está aquí.`), the italic greeting (`Hola Jerson,`), the P. D. caption, and the footer Legal lines.
- **Gotham** — body, subhead labels, button. Self-hosted from the website at `https://oqupa.com/fonts/Gotham{Book,Medium,Bold}.otf`.

Both font families are loaded via `@font-face` in the email's `<style>` block. The fallback chain mirrors the website verbatim:
- Sans: `'Gotham', -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`
- Serif: `'Roboto Serif', Georgia, 'Times New Roman', serif`

`@font-face` works in Apple Mail (macOS + iOS), Outlook 365 (web/Mac/new Windows), and Yahoo Mail. **Gmail and Outlook 2007–2019 desktop strip `@font-face` entirely**, so those recipients see the system-sans fallback (Helvetica or Segoe UI). This is the same compatibility behavior our website has — no workaround short of rasterizing text.

### Color palette
The badges and CTA use a monochromatic orange progression — same single-hue cohesion that Stripe (purple), Airbnb (coral), Linear (purple) use. Four stops:

| Stop | Hex | Source |
|---|---|---|
| Light peach | `#FBA075` | Tailwind orange-300/400 neighbor of brand |

| Hover | `#E0632E` | `--color-primary-hover` |

Each badge gradient is a 135° wash that overlaps with the next badge's range, creating a visual "warmth crescendo" from Card 1 to Card 3:

The accent yellow `#FFCD60` (`--color-accent`) appears in only one place: the `GRATIS` pill on Card 2. Deliberate non-orange accent on the value-prop callout.

## Email-engineering decisions

| Decision | Reason |
|---|---|
| Table-based layout | Outlook desktop uses Word's renderer — flex/grid don't work |
| `meta name="color-scheme" content="light"` + `supported-color-schemes` | Locks light mode so Apple Mail / iOS / Gmail dark mode don't auto-invert our cream and orange into a muddy dark scheme |
| `meta name="format-detection" content="telephone=no, date=no, address=no, email=no"` | Stops iOS Mail and Outlook from auto-linking phone numbers, dates, and addresses with default blue underlines |
| `a[x-apple-data-detectors]` reset rule | Same idea — neutralizes iOS Mail's heuristic styling on detected entities |
| VML `<v:roundrect>` for the CTA in `<!--[if mso]>` | Outlook 2007–2019 ignores `border-radius`. The VML round-rect renders the pill button correctly with `arcsize="50%"` |
| `mso-line-height-alt` on every line-height | Outlook ignores `line-height` and uses its own. `mso-line-height-alt` is the absolute-pixel override for Outlook only |
| Self-hosted Gotham via `@font-face` | Brand-faithful where supported. Gmail/Outlook desktop fall back to the system stack — same behavior as the website |
| Hidden preheader `<div>` with `font-size:1px; color:matches-bg` | The text shown next to the subject in inbox previews on Gmail / Apple Mail — without this, Gmail picks a random snippet from the email body |
| `@media (max-width: 620px)` for mobile | Single column already; just collapses the 600px container to full width and reduces side padding from 40px to 24px |
| Single-purpose campaign (no fake nav, no event tiles, no preference center) | This is a launch announcement, not a newsletter. Every section earns its place |

## Sender setup

**From header:** `Oqupa <equipo@oqupa.com>`
**Reply-To:** `equipo@oqupa.com`

`equipo@oqupa.com` is a Google Workspace alias on `admin@oqupa.com`, configured at `admin.google.com → Directory → Users → admin@oqupa.com → Alternate email addresses`. Inbound mail to `equipo@` lands in `admin@`'s inbox; Gmail auto-registered it as a Send-As alias, so the SMTP relay (used by the Trigger Email extension) accepts the rewritten From header without DMARC issues.

**SMTP transport:** `firebase/firestore-send-email@0.2.4` Firebase extension, configured at `Oqupa-website/extensions/firestore-send-email.env`. Connects to Gmail SMTP (`smtps://admin@oqupa.com@smtp.gmail.com:465`) using a Gmail App Password stored in Secret Manager (`projects/109922131848/secrets/ext-firestore-send-email-SMTP_PASSWORD/versions/1`).

The extension watches the `mail` collection. We write one doc per recipient with `to`, `from`, `replyTo`, `message.{subject,html}`. The extension dispatches, retries on failure, and writes a `delivery` field back onto each doc with the result.

## Static landing page

A copy of the rendered email is hosted at `https://oqupa.com/email/launch.html` for the "view in browser" link. It's generated from `index.html` by a one-shot `sed` substitution:

```bash
sed \
  -e 's|{{firstName}}|amigo|g' \
  -e 's|{{viewInBrowserUrl}}|#|g' \
  -e 's|{{unsubscribeUrl}}|mailto:equipo@oqupa.com?subject=Unsubscribe|g' \
  -e 's|\.\./\.\./public/email/|https://oqupa.com/email/|g' \
  Oqupa-website/email/launch-2026-05-04/index.html \
  > Oqupa-website/public/email/launch.html
```

If `index.html` is updated, regenerate `launch.html` with the same command and re-deploy the website. Both files are in the website repo and ship via the normal master-branch deploy pipeline.

## Send process

The script `send.cjs` is dry-run by default. It uses `firebase-admin` with Application Default Credentials, so the operator needs `gcloud auth application-default login` for `oqupa-production`.

```bash
# Set NODE_PATH once per shell so firebase-admin is resolvable
export NODE_PATH=/Users/jerson/developer/Oqupa-Platform/oqupa/functions/node_modules

# 1. Dry run — print the recipient list, write nothing
node Oqupa-website/email/launch-2026-05-04/send.cjs

# 2. Test send — queue one mail doc to a single address (does NOT mark
#    the campaign as sent; safe to run multiple times)
node Oqupa-website/email/launch-2026-05-04/send.cjs --test=jerson.7@icloud.com

# 3. Real send — atomically queue all 37 mail docs and write
#    `campaigns/may4_launch.sentAt`. Idempotent: re-running aborts unless --force.
node Oqupa-website/email/launch-2026-05-04/send.cjs --send
```

After `--send`:
- `campaigns/may4_launch` Firestore doc records `sentAt` and `count`
- Audit log written to `/tmp/oqupa_launch/sent_<ISO-timestamp>.json` (recipient list with doc IDs, outside the repo)
- The Trigger Email extension picks up the docs from `mail` and dispatches via Gmail SMTP. Delivery typically completes within a couple of minutes.

To inspect dispatch status, look at the `delivery` field that the extension writes back onto each `mail/{docId}` document in Firestore.

## Known limitations

- **Mailto unsubscribe.** For 37 recipients this is acceptable — replies land in `admin@oqupa.com`'s inbox, where they need to be honored manually. For a real cadence campaign, build a tokenized one-click endpoint (signed token → CF → write `unsubscribed/{email}`).
- **Single shared view-in-browser page.** Everyone sees the same `launch.html` with a generic `Hola amigo,` salutation. No per-recipient personalization in the browser version. Fine for a one-off.
- **No bounce / complaint handling.** Gmail SMTP returns delivery receipts to `admin@oqupa.com`. Hard bounces should be reviewed and the corresponding docs flagged. We're not automating this for 37 recipients.
- **Idempotency is per-campaign-id, not per-recipient.** `--force` re-queues the entire batch. If you need to resend to a single address, use `--test=<email>` instead.
- **Plus-aliased addresses.** `jersondevs@gmail.com` and `jersondevs+appstore@gmail.com` are in the user list as separate accounts but deliver to the same inbox. Not filtered. Operator's call whether to manually skip.

## After this launch

If we run more campaigns, the things worth promoting:

1. **Tokenized unsubscribe endpoint** (Cloud Function + signed token + `unsubscribed/{email}` collection)
2. **Bounce/complaint webhook** from the SMTP transport, writing back to Firestore
3. **Reusable template engine** — extract `index.html` placeholder substitution into a shared module so future campaigns just write copy + assets
4. **Schedule sends instead of running locally** — convert `send.cjs` into a callable Cloud Function so non-developers can trigger campaigns from a small admin UI
